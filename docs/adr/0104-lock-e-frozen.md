# ADR-0104 — `loxia.lock`: hash de árvore, `--frozen` e cache local

- **Status:** accepted (implementado)
- **Data:** 2026-11-17
- **Decisores:** Cássio + agente (DSH)
- **Relacionados:** [ADR-0100](0100-dependencias-path.md) (dependências `path`),
  [ADR-0088](0088-distribuicao-e-raizes-de-modulo.md) (raízes e `loxia.toml`),
  [ADR-0075](0075-diagnosticos-estruturados.md) (códigos), [ADR-0093](0093-cli-agent-friendly-e-reparo.md)
  (contrato do CLI), [`../../TODO.md`](../../TODO.md) §14.7 (fase 1),
  [`../../IDEIAS.md`](../../IDEIAS.md) I-10
- **Implementação:** `loxia_core/loader/lock.py`, `loxia_core/loader/deps.py`,
  `loxia_core/loader/manifest.py`, `loxia/cli.py` (`lock`, `fetch`, `--frozen`,
  `--offline`, `--cache-dir`) e `tests/test_dependencies.py`

## Contexto

O [ADR-0100](0100-dependencias-path.md) fez `import acme.foo` resolver pelo nome declarado
em `[dependencies]`, mas o manifest sozinho não é reprodutível: o diretório da dependência
pode mudar de conteúdo entre duas execuções e nada acusa. O produto vende I3 (mesma entrada
⇒ mesmos bytes); um gerenciador de pacotes sem lock contradiria isso.

A fase 1 do §14.7 pedia `loxia.lock` com versão exata + `sha256`, `loxia lock`,
`loxia fetch --offline` e cache local. Hoje só existe dependência `path` — não há versão
semântica nem download —, então o lock precisa provar **conteúdo** e **identidade** sem
inventar semver.

## Decisão

### 1. O lock mora na pasta do manifest e é versionado

`loxia.lock` fica ao lado de `loxia.toml`, é gerado por `loxia lock` e entra no git. É um
artefato de reprodutibilidade, não configuração: ninguém edita à mão.

### 2. Formato canônico

```toml
# Generated by `loxia lock`; do not edit.
version = 1

[[package]]
name = "acme"
path = "../acme"
version = "0.1.0"
sha256 = "…"
```

- `version` é a versão do **schema** do lock (não do projeto).
- Uma entrada por dependência, ordenada por `name`; chaves em ordem fixa; LF; cabeçalho
  fixo. O renderizador é a única fonte do texto, então dois manifests iguais produzem
  **bytes** iguais (teste de determinismo).
- `path` é relativo à pasta do manifest, em posix. Caminho absoluto é erro de parse;
  nenhuma máquina/`CWD` entra no arquivo.
- `version` é a `[package].version` da dependência quando ela declara uma (opcional nesta
  fase; obrigatória para dependência `git` no ADR-0105, fase 2).
- `git`/`rev`/`commit` já são aceitos no parser e reservados para a fase 2; nesta fase só
  `path` é emitido.

### 3. O hash é da árvore de fontes

`sha256` identifica o **conteúdo**: percorre `*.lx` da raiz da dependência, ordena pelo
caminho relativo posix e alimenta `caminho + "\0" + sha256(bytes) + "\n"` no digest final.
Somente `.lx` conta — é o que o loader compila; `.git`, `loxia.lock` e assets não entram.
Symlink que resolve para fora da raiz é erro (mesma regra do ADR-0088).

Consequência: renomear um arquivo, mudar um byte ou adicionar um módulo mudam o hash;
`touch` e ordem de diretório não mudam.

### 4. Identidade = nome + origem + versão

O lock fixa `name` (a chave do manifest), a origem (`path` relativo) e a `version`
declarada. O path sozinho não é identidade: renomear a pasta ou mover o pacote sem mudar o
manifest invalida o lock e obriga um `loxia lock` explícito.

### 5. `[package].version` é `X.Y.Z` e opcional

O campo entra em `[package]` no manifest, validado como `X.Y.Z` (sem ranges, pré-release
ou build metadata). É opcional para projeto e para dependência `path`; o lock grava quando
existe. Semver completo (ranges, backtracking) continua fora ([`IDEIAS.md`](../../IDEIAS.md) I-10).

### 6. Comandos e flags

- `loxia lock` — calcula a árvore a partir do manifest e grava `loxia.lock`.
- `loxia lock --check` — não escreve; exit `1` se o lock no disco difere do calculado
  (mesma convenção de `fmt --check`), com mensagem de uma linha no stderr.
- `loxia fetch` — verifica que a árvore local bate com o lock (fase 1: hashes dos paths;
  fase 2: checkouts git). Não compila o projeto.
- `loxia fetch --offline` — proíbe rede. Na fase 1 é um no-op para `path`; existe para
  a fase 2 e para o contrato do CLI.
- `--frozen` em `run`/`check`/`build`/`ast`/`test` — resolve **só** pelo lock: lock
  ausente com dependências, pacote ausente/extra, versão ou hash diferentes viram erro
  `C0002` (exit 65). Sem manifest, `--frozen` é erro; projeto sem dependências dispensa
  lock.
- `--cache-dir DIR` — cache de dependências; o default é `.loxia/cache/` na raiz do
  projeto. Nada de `HOME` nem variável de ambiente no caminho de resolução.
- `loxia test` repassa `--frozen`/`--offline`/`--cache-dir` aos subprocessos de run/build.

### 7. Rede só em comandos explícitos

`run`/`check`/`build`/`ast`/`test` **nunca** acessam a rede. Somente `loxia lock` e
`loxia fetch` podem, e `--offline` proíbe até eles. Na fase 2 isso vale para `git`; na fase
1 o lock/fetch já obedecem à regra para não mudar contrato depois.

### 8. Diagnóstico `C0002`

Estado de lock/dependência (ausente, desatualizado, não baixado) usa o código novo
`C0002` na fase `cli`; manifest inválido continua `E1001` (parser). Mensagens nunca citam
caminho absoluto.

### 9. Fora de escopo (explícito)

- Dependências transitivas: só o manifest raiz declara; o lock é plano.
- `std` não entra no lock: a versão da stdlib é a do compilador (ADR-0088).
- `[modules].paths` não entra no lock: são raízes soltas, sem identidade de pacote.
- Registry, tarballs, semver com ranges e pacote binário: §14.7 fases 3+.

## Consequências

### Positivas

- "Mesmo manifest + lock ⇒ mesma árvore e mesmo build" deixa de ser promessa e vira teste.
- Drift de dependência `path` passa a ser detectável (`--frozen`, `fetch`, `lock --check`).
- CI pode rodar `--frozen` sem rede e falhar cedo se alguém esqueceu de regravar o lock.
- O loader continua ignorante de lock/cache: recebe raízes resolvidas. A fase 2 acrescenta
  git sem tocar na resolução de módulos.

### Negativas / custos

- Editar uma dependência `path` invalida o lock; o fluxo é "edita → `loxia lock`" antes de
  rodar `--frozen`.
- `--frozen` recalcula o hash da árvore a cada execução (O(bytes) das dependências).
- O lock é mais um arquivo para versionar e revisar em cada mudança de dependência.
- Na fase 1 `fetch` é verificação, não download; o nome só ganha o sentido completo com git.

### Neutras

- Cache por projeto duplica conteúdo entre projetos; a fase 2 pode oferecer `--cache-dir`
  compartilhado sem mudar a semântica.
- O hash cobre só `.lx`; assets de runtime que não são fontes da linguagem ficam fora.

## Alternativas consideradas

| Alternativa | Por que não |
| --- | --- |
| Lock só com nome/path/ordem, sem hash | Não prova conteúdo; contradiz "lock com hash" da §14.7. |
| Hash por mtime/tamanho | Não determinístico entre máquinas e checkouts. |
| Cache global em `~/.cache/loxia` | Depende de `HOME` e enfraquece "sem ambiente"; I3 fica mais difícil de auditar. |
| Semver/ranges no lock agora | Não há registry nem segundo publicador; ranges sem resolução real são teatro. |
| Fazer lock só junto com git | Adia a reprodutibilidade que já é vendida e escreve a fase 1 duas vezes. |
